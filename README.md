# buy-or-not (살까 말까)

무신사 링크를 붙여넣어 가진 옷을 옷장으로 등록하고, 새로 살까 고민 중인 옷의 링크를 넣으면 옷장의 실측·선호도와 비교해 살만한지 판단해주는 개인 프로젝트. 취업 준비용 사이드 프로젝트로 진행 중이며, 겪은 문제와 해결 과정을 Phase 단위로 아래에 기록한다.

## 진행 기록

### Phase 0 — 무신사 파싱 타당성 조사 (2026-08-15)

**문제**: 무신사는 공식 API가 없다. 상품 페이지를 스크래핑해야 하는데, 특히 실측치(총장·가슴단면 등)를 어디서 얻을 수 있는지가 파서·저장 구조·등록 화면 UX를 전부 좌우해서, 코드를 짜기 전에 먼저 확인이 필요했다.

**조사 방법**: `curl`로 실제 상품 페이지(상의·하의·아우터 3개 카테고리)의 HTML을 받아 분석하고 `robots.txt`를 확인했다. 실측 데이터가 정적 HTML에 없어서, 브라우저에서 직접 페이지를 열어 개발자도구 Network 탭·Resource Timing API·`fetch`/`XHR` 몽키패치까지 동원해 그 값이 어떤 경로로 들어오는지 추적했다.

**발견**:
1. **robots.txt**: 이름이 지정된 봇(주요 검색엔진, AI 에이전트)만 `Allow`하고 나머지 User-Agent는 전부 `Disallow: /`. 이 프로젝트의 서버 fetcher는 이 허용 목록에 없다.
2. **상품 기본 정보**(이름·브랜드·가격·이미지·카테고리)는 서버가 내려주는 정적 HTML 안 `__NEXT_DATA__` 스크립트에 JSON으로 이미 들어있어서, 헤드리스 브라우저 없이 `fetch` 한 번으로 가져올 수 있었다.
3. **실측치 테이블**은 정적 HTML에도, 위 JSON에도, 관찰 가능한 어떤 네트워크 요청에도 나타나지 않았다 — 브라우저가 렌더링한 뒤에야 DOM에 나타나는데, 그 값이 어디서 오는지 끝내 특정하지 못했다.

**해결**: 실측치는 "무신사 페이지의 사이즈 표를 사용자가 통째로 복사해서 붙여넣으면, 클립보드 HTML 구조를 그대로 파싱해 자동으로 채워주는" 방식으로 설계를 바꿨다. 단순 수동 타이핑보다 마찰이 적고, 한 사용자가 붙여넣은 표는 캐시에 반영되어 다음 사용자는 이 단계 자체를 건너뛴다. Selenium 같은 헤드리스 브라우저 크롤러는 검토했지만 기각했다 — robots.txt 문제를 그대로 안고 가는 데다, 서버에 무거운 브라우저 인프라를 얹는 비용이 이 방식으로 얻는 이득보다 컸다.

**결과**: 설계 스펙과 구현 계획을 실제로 확인된 구조에 맞게 다시 썼다. 상품 기본 정보는 자동 파싱, 실측치는 사용자 붙여넣기 기반 자동 파싱으로 역할을 나누는 구조로 Phase 1(기반) 착수 전에 정리를 마쳤다.
