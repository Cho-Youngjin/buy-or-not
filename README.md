# buy-or-not (살까 말까)

무신사 링크를 붙여넣어 가진 옷을 옷장으로 등록하고, 새로 살까 고민 중인 옷의 링크를 넣으면 옷장의 실측·선호도와 비교해 살만한지 판단해주는 개인 프로젝트. 취업 준비용 사이드 프로젝트로 진행 중이며, 겪은 문제와 해결 과정을 Phase 단위로 아래에 기록한다.

## 진행 기록

### Phase 0 — 무신사 파싱 타당성 조사 (2026-08-15)

**문제**: 무신사는 공식 API가 없다. 상품 페이지를 스크래핑해야 하는데, 특히 실측치(총장·가슴단면 등)를 어디서 얻을 수 있는지가 파서·저장 구조·등록 화면 UX를 전부 좌우해서, 코드를 짜기 전에 먼저 확인이 필요했다.

**조사 방법**: `curl`로 실제 상품 페이지(상의·하의·아우터 3개 카테고리)의 HTML을 받아 분석하고 `robots.txt`를 확인했다. 실측 데이터가 정적 HTML에 없어서, 브라우저에서 직접 페이지를 열어 개발자도구 Network 탭·Resource Timing API·`fetch`/`XHR` 몽키패치까지 동원해 그 값이 어떤 경로로 들어오는지 추적했다.

**발견**:
1. **robots.txt**: 이름이 지정된 봇(주요 검색엔진, AI 에이전트)만 `Allow`하고 나머지 User-Agent는 전부 `Disallow: /`. 이 프로젝트의 서버 fetcher는 이 허용 목록에 없다.
2. **상품 기본 정보**(이름·브랜드·가격·이미지·카테고리)는 서버가 내려주는 정적 HTML 안 `__NEXT_DATA__` 스크립트에 JSON으로 이미 들어있어서, 헤드리스 브라우저 없이 `fetch` 한 번으로 가져올 수 있었다.
3. **실측치 테이블**은 정적 HTML에도, 위 JSON에도, 관찰 가능한 어떤 네트워크 요청에도 나타나지 않았다 — 브라우저가 렌더링한 뒤에야 DOM에 나타나는데, 그 값이 어디서 오는지 끝내 특정하지 못했다.

**해결**: 실측치는 "무신사 페이지의 사이즈 표를 사용자가 통째로 복사해서 붙여넣으면, 클립보드 HTML 구조를 그대로 파싱해 자동으로 채워주는" 방식으로 설계를 바꿨다. 단순 수동 타이핑보다 마찰이 적고, 한 사용자가 붙여넣은 표는 캐시에 반영되어 다음 사용자는 이 단계 자체를 건너뛴다. Selenium 같은 헤드리스 브라우저 크롤러는 검토했지만 기각했다 — robots.txt 문제를 그대로 안고 가는 데다, 서버에 무거운 브라우저 인프라를 얹는 비용이 이 방식으로 얻는 이득보다 컸다.

**결과**: 설계 스펙과 구현 계획을 실제로 확인된 구조에 맞게 다시 썼다. 상품 기본 정보는 자동 파싱, 실측치는 사용자 붙여넣기 기반 자동 파싱으로 역할을 나누는 구조로 Phase 1(기반) 착수 전에 정리를 마쳤다.

### Phase 1 — 기반 (2026-08-15)

Next.js 프로젝트 셋업부터 Supabase 스키마·RLS·구글 로그인까지, 로그인해서 빈 옷장(아직 없는 페이지라 404)을 보는 것까지가 목표였다.

**겪은 문제 1 — 기존 파일과 `create-next-app`의 충돌**

**문제**: 리포에 이미 `CLAUDE.md`, `docs/`, `tests/` 같은 파일이 있는 상태에서 `create-next-app`을 돌리면, 도구가 "충돌 가능성이 있다"며 아예 실행을 거부한다.

**해결**: 임시 폴더에 스캐폴드를 생성한 뒤 `app/`, `package.json`, 설정 파일들만 리포 루트로 옮기고, 기존 문서·테스트 파일은 그대로 뒀다. `.gitignore`도 Next.js 기본 템플릿과 병합하면서 `.env*` 같은 넓은 패턴이 `.env.local.example`(커밋해야 하는 템플릿 파일)까지 가려버리지 않게 `.env`/`.env.local`/`.env*.local`로 좁혀서 썼다.

**겪은 문제 2 — Supabase 마이그레이션이 `gen_random_bytes`에서 실패**

**문제**: 가입 트리거 마이그레이션(`0003_profile_trigger.sql`)을 원격 Supabase 프로젝트에 적용하는데 `function gen_random_bytes(integer) does not exist` 오류가 났다.

**원인**: Supabase 호스팅 프로젝트는 `pgcrypto` 같은 공용 확장을 `public` 스키마가 아니라 `extensions` 스키마에 설치해둔다. 함수 본문에서 스키마를 명시하지 않고 `gen_random_bytes(9)`를 부르면, 그 시점의 `search_path`에 `extensions`가 없어서 함수를 찾지 못한다. (반면 `gen_random_uuid()`는 PostgreSQL 13+의 코어 내장 함수라 이 문제가 없었다 — 같은 마이그레이션 파일 안에서 하나는 되고 하나는 안 되는 이유였다.)

**해결**: `extensions.gen_random_bytes(9)`로 스키마를 명시적으로 붙였다. 로컬 Docker 없이 원격 프로젝트에 직접 `supabase db push`를 반복하며 잡은 문제라, 실제 호스팅 환경의 스키마 배치를 직접 겪어보지 않았다면 놓치기 쉬웠다.

**검증**: RLS 정책은 실제 원격 DB에 두 명의 테스트 유저(소유자/제3자)를 만들어 "남의 비공개 옷장 조회 차단", "공개 옷장 조회 허용", "추천만 가능하고 소유자 사칭은 불가", "남의 옷 수정·삭제 불가", "일반 사용자는 `musinsa_cache` 접근 불가" 등 9개 시나리오를 실제로 통과시켜 검증했다(정책 문구만 보고 맞다고 가정하지 않았다). 구글 로그인도 실제 OAuth 플로우를 끝까지 돌려 `/wardrobe`로 리디렉트되고 `profiles` 행이 트리거로 자동 생성되는 것까지 확인했다.

**결과**: Phase 1 완료 기준(로그인 → 빈 옷장 경로) 충족. Docker 없이 원격 Supabase 프로젝트만으로 개발 사이클(마이그레이션 작성 → `db push` → 테스트/수동 검증)을 완성했다.
