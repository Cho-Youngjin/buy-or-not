# buy-or-not (살까 말까)

무신사 링크를 붙여넣어 가진 옷을 옷장으로 등록하고, 새로 살까 고민 중인 옷의 링크를 넣으면 옷장의 실측·선호도와 비교해 살만한지 판단해주는 개인 프로젝트. 취업 준비용 사이드 프로젝트로 진행 중이며, 겪은 문제와 해결 과정을 Phase 단위로 아래에 기록한다.

## 진행 기록

### Phase 0 — 무신사 파싱 타당성 조사 (2026-08-15)

**문제**: 무신사는 공식 API가 없다. 상품 페이지를 스크래핑해야 하는데, 특히 실측치(총장·가슴단면 등)를 어디서 얻을 수 있는지가 파서·저장 구조·등록 화면 UX를 전부 좌우해서, 코드를 짜기 전에 먼저 확인이 필요했다.

**조사 방법**: `curl`로 실제 상품 페이지(상의·하의·아우터 3개 카테고리)의 HTML을 받아 분석하고 `robots.txt`를 확인했다. 실측 데이터가 정적 HTML에 없어서, 브라우저에서 직접 페이지를 열어 개발자도구 Network 탭·Resource Timing API·`fetch`/`XHR` 몽키패치까지 동원해 그 값이 어떤 경로로 들어오는지 추적했다.

**발견**:
1. **robots.txt**: 이름이 지정된 봇(주요 검색엔진, AI 에이전트)만 `Allow`하고 나머지 User-Agent는 전부 `Disallow: /`. 이 프로젝트의 서버 fetcher는 이 허용 목록에 없다.
2. **상품 기본 정보**(이름·브랜드·가격·이미지·카테고리)는 서버가 내려주는 정적 HTML 안 `__NEXT_DATA__` 스크립트에 JSON으로 이미 들어있어서, 헤드리스 브라우저 없이 `fetch` 한 번으로 가져올 수 있었다.
3. **실측치 테이블**은 정적 HTML에도, 위 JSON에도, 관찰 가능한 어떤 네트워크 요청에도 나타나지 않았다 — 브라우저가 렌더링한 뒤에야 DOM에 나타나는데, 그 값이 어디서 오는지 끝내 특정하지 못했다.

**해결**: 실측치는 "무신사 페이지의 사이즈 표를 사용자가 통째로 복사해서 붙여넣으면, 클립보드 HTML 구조를 그대로 파싱해 자동으로 채워주는" 방식으로 설계를 바꿨다. 단순 수동 타이핑보다 마찰이 적고, 한 사용자가 붙여넣은 표는 캐시에 반영되어 다음 사용자는 이 단계 자체를 건너뛴다. Selenium 같은 헤드리스 브라우저 크롤러는 검토했지만 기각했다 — robots.txt 문제를 그대로 안고 가는 데다, 서버에 무거운 브라우저 인프라를 얹는 비용이 이 방식으로 얻는 이득보다 컸다.

**결과**: 설계 스펙과 구현 계획을 실제로 확인된 구조에 맞게 다시 썼다. 상품 기본 정보는 자동 파싱, 실측치는 사용자 붙여넣기 기반 자동 파싱으로 역할을 나누는 구조로 Phase 1(기반) 착수 전에 정리를 마쳤다.

### Phase 1 — 기반 (2026-08-15)

Next.js 프로젝트 셋업부터 Supabase 스키마·RLS·구글 로그인까지, 로그인해서 빈 옷장(아직 없는 페이지라 404)을 보는 것까지가 목표였다.

**겪은 문제 1 — 기존 파일과 `create-next-app`의 충돌**

**문제**: 리포에 이미 `CLAUDE.md`, `docs/`, `tests/` 같은 파일이 있는 상태에서 `create-next-app`을 돌리면, 도구가 "충돌 가능성이 있다"며 아예 실행을 거부한다.

**해결**: 임시 폴더에 스캐폴드를 생성한 뒤 `app/`, `package.json`, 설정 파일들만 리포 루트로 옮기고, 기존 문서·테스트 파일은 그대로 뒀다. `.gitignore`도 Next.js 기본 템플릿과 병합하면서 `.env*` 같은 넓은 패턴이 `.env.local.example`(커밋해야 하는 템플릿 파일)까지 가려버리지 않게 `.env`/`.env.local`/`.env*.local`로 좁혀서 썼다.

**겪은 문제 2 — Supabase 마이그레이션이 `gen_random_bytes`에서 실패**

**문제**: 가입 트리거 마이그레이션(`0003_profile_trigger.sql`)을 원격 Supabase 프로젝트에 적용하는데 `function gen_random_bytes(integer) does not exist` 오류가 났다.

**원인**: Supabase 호스팅 프로젝트는 `pgcrypto` 같은 공용 확장을 `public` 스키마가 아니라 `extensions` 스키마에 설치해둔다. 함수 본문에서 스키마를 명시하지 않고 `gen_random_bytes(9)`를 부르면, 그 시점의 `search_path`에 `extensions`가 없어서 함수를 찾지 못한다. (반면 `gen_random_uuid()`는 PostgreSQL 13+의 코어 내장 함수라 이 문제가 없었다 — 같은 마이그레이션 파일 안에서 하나는 되고 하나는 안 되는 이유였다.)

**해결**: `extensions.gen_random_bytes(9)`로 스키마를 명시적으로 붙였다. 로컬 Docker 없이 원격 프로젝트에 직접 `supabase db push`를 반복하며 잡은 문제라, 실제 호스팅 환경의 스키마 배치를 직접 겪어보지 않았다면 놓치기 쉬웠다.

**검증**: RLS 정책은 실제 원격 DB에 두 명의 테스트 유저(소유자/제3자)를 만들어 "남의 비공개 옷장 조회 차단", "공개 옷장 조회 허용", "추천만 가능하고 소유자 사칭은 불가", "남의 옷 수정·삭제 불가", "일반 사용자는 `musinsa_cache` 접근 불가" 등 9개 시나리오를 실제로 통과시켜 검증했다(정책 문구만 보고 맞다고 가정하지 않았다). 구글 로그인도 실제 OAuth 플로우를 끝까지 돌려 `/wardrobe`로 리디렉트되고 `profiles` 행이 트리거로 자동 생성되는 것까지 확인했다.

**결과**: Phase 1 완료 기준(로그인 → 빈 옷장 경로) 충족. Docker 없이 원격 Supabase 프로젝트만으로 개발 사이클(마이그레이션 작성 → `db push` → 테스트/수동 검증)을 완성했다.

### Phase 2 — 옷장 등록 (2026-08-15)

무신사 링크를 붙여넣어 색상·사이즈를 고르면 실측과 함께 옷장에 저장되고 그리드로 조회되는 것까지가 목표였다. 파싱 API·캐시(Task 9), 링크 입력·옵션 선택 화면(Task 10), 등록 API(Task 11), 옷장 그리드(Task 12) 순서로 진행했다.

**겪은 문제 — Supabase Storage가 한글 오브젝트 키를 거부**

**문제**: 실제 무신사 링크(`/products/6593921`)로 등록까지 전체 플로우를 브라우저에서 검증하는 중, `garments` 테이블에는 행이 정상적으로 쌓였지만 `image_url`이 Storage 사본 URL이 아니라 무신사 CDN 원본 URL 그대로 저장돼 있었다. `storage.objects`를 조회해보니 아예 파일이 하나도 없었다 — 이미지 복사(`copyImageToStorage`)가 매번 조용히 실패하고 있었다.

**원인**: 이 함수는 예외 대신 실패 시 저장을 막지 않으려고 실패를 전부 삼켜서(`try { … } catch { return null }`) 실패 자체는 등록을 방해하지 않지만, 원인도 함께 감춰버렸다. 별도 스크립트로 `copyImageToStorage`와 동일한 fetch→업로드 과정을 그대로 재현해 에러를 직접 찍어보니 `StorageApiError: Invalid key`였다. 오브젝트 경로를 만들 때 색상명(`색상 문자열 → 정규식으로 안전화`)에 쓴 정규식이 `[^\p{L}\p{N}]+`(유니코드 "문자·숫자"는 전부 허용)였는데, 한글도 유니코드 Letter 카테고리라 그대로 통과됐다. 문제는 Supabase Storage 쪽 — 오브젝트 키에 비-ASCII 문자(한글 포함)를 아예 허용하지 않는다. 무신사 색상 옵션은 "블랙"·"화이트"처럼 거의 항상 한국어라 이 경로는 사실상 항상 실패하는 구조였다.

**해결**: 색상명을 경로에 그대로 쓰는 대신 `crypto.createHash('sha1')`로 짧은 해시를 만들어 오브젝트 키(`{goodsNo}/{해시}.{확장자}`)를 구성하도록 `lib/storage.ts`를 고쳤다. 이 경로는 사용자에게 노출되지 않고(공개 URL만 노출된다) 같은 색상이면 항상 같은 해시가 나와 재등록 시 `upsert`로 재사용된다.

**검증**: 유닛 테스트·`npm run build`만으로는 이 버그가 드러나지 않았다(둘 다 네트워크·실제 Storage 호출이 없는 경로라서). 로그인된 브라우저 세션으로 실제 무신사 링크를 붙여넣어 끝까지 등록해보고, Supabase에 직접 SQL로 `garments`/`garment_measurements`/`storage.objects`를 조회해서야 잡아냈다 — 수정 후 같은 플로우를 다시 돌려 `image_url`이 Storage 공개 URL로 바뀌고 `storage.objects`에 파일이 생기는 것까지 확인했다. 테스트로 등록했던 옷 2벌과 이미지 파일은 검증 후 정리했다.

**겪은 문제 — 사이즈표 붙여넣기가 실제 무신사 페이지에서는 값이 한 칸씩 밀려서 들어감**

**문제**: 위 버그를 고친 뒤 실제 사용해보니, 사용자가 무신사 "사이즈" 탭 표를 직접 드래그해서 복사·붙여넣었는데도 사이즈별 실측값이 자동으로 채워지지 않았다. 붙여넣은 원문을 확인해보니 `cm / 내 사이즈 / M / L / XL`(라벨)이 먼저 나오고, 그 다음에 `총장 어깨너비 가슴단면 소매길이`(헤더)와 숫자 행들이 따로 이어지는, Task 5-1에서 가정했던 "한 표에 라벨 칸 포함" 구조와 다른 순서였다.

**원인**: 실제 상품 페이지를 열어 DOM을 직접 조사해보니(`document.querySelectorAll('table')`, `<li>` 탐색), 사이즈 라벨(cm/내 사이즈/M/L/XL)은 `<table>`이 아니라 `<ul><li>`로 만든 별도의 고정(sticky) 열이고, 실측값은 라벨 칸이 아예 없는 별도의 `<table>`이었다 — 표 폭이 넓어질 수 있는 하의 등에서 첫 열을 고정하기 위한 흔한 UI 패턴으로 보인다. Phase 0 조사 때는 "실측표는 정적 HTML에 없다"까지만 확인했을 뿐, 사용자가 실제로 드래그해서 복사했을 때 이 두 DOM이 어떤 순서로 클립보드에 담기는지는 확인하지 못한 상태였다. 기존 파서(`rowsFromHtml`)는 `<tr>`만 찾아서 `<li>` 라벨 자체를 통째로 무시했고, 표 조립 로직(`buildTable`)은 "헤더 첫 칸=라벨, 데이터 행 첫 칸=사이즈명"이라고 잘못 가정해서 총장 값이 통째로 날아가고 숫자(61 등)가 사이즈명으로 오인되는 결과를 냈다.

**해결**: `lib/musinsa/pasteSizeTable.ts`를 실제 구조에 맞춰 다시 짰다. HTML 파싱 시 `<tr>`뿐 아니라 `<li>`도 문서 순서 그대로 수집하고, "칸이 1개뿐인 행 = 라벨 후보", "헤더와 칸 수가 같고 숫자가 있는 행 = 측정 데이터"로 나눠 각각 모은 뒤, 라벨 목록을 뒤에서부터(= `cm`·`내 사이즈` 같은 실제 사이즈가 아닌 항목이 자연히 걸러지도록) 데이터 행 개수만큼 잘라 순서대로 짝지었다.

**검증**: 실제 상품 페이지의 사이즈 탭 DOM을 브라우저 자바스크립트로 직접 읽어 라벨(`<li>`)·측정값(`<table>`) 구조를 확인한 뒤, 그 구조를 그대로 재현한 테스트 픽스처로 유닛 테스트를 다시 작성해 9개 모두 통과시켰다. 브라우저 자동화로 실제 Ctrl+C/Ctrl+V 클립보드 이벤트까지 재현하려 했으나 페이지가 자동화 드래그 중 응답 없음 상태가 되어 끝까지 재현하지 못했다 — 이 부분은 사용자가 직접 다시 붙여넣어 확인하기로 했다.

**결과**: Phase 2 완료 기준(무신사 링크 → 옵션 선택 → 실측 저장 → Storage 이미지 복사 → 옷장 그리드 표시) 충족. `npm test`(53개) 전부 통과, `npm run build` 타입 오류 없이 성공. Phase 0에서 "확인 안 됨"으로 남겨뒀던 부분(실측표를 실제로 복사했을 때의 클립보드 구조)이 사용자 실사용 중에 드러난 사례 — 사전 조사만으로는 잡을 수 없고 실제 사용 피드백이 필요한 종류의 문제였다.

### Phase 3 — 옷장 상세와 선호도 (2026-08-15)

옷 상세 화면에서 실측을 보고, 별점·핏 태그·착용빈도를 남기고, 삭제할 수 있는 것까지가 목표였다. `PATCH`/`DELETE /api/garments/:id`와 `/wardrobe/[id]` 페이지를 만들었다.

**겪은 문제 — Supabase JS의 `update()`/`delete()`에 `count` 옵션을 잘못된 위치에 넘김**

**문제**: "몇 행이 갱신·삭제됐는지"로 남의 옷(RLS가 막아 0행 처리됨)과 존재하지 않는 옷(404)을 구분하려고 `.update(values).eq('id', id).select('id', { count: 'exact', head: true })`처럼 `select()`에 `count` 옵션을 얹었더니 `npm run build`에서 "Expected 0-1 arguments, but got 2" 타입 에러가 났다.

**원인**: `@supabase/postgrest-js`의 소스(`node_modules/@supabase/postgrest-js/src/PostgrestQueryBuilder.ts`)를 직접 열어보니, `count`는 `update()`/`delete()`/`insert()`/`upsert()` 자신이 두 번째 인자로 받는 옵션이었다 — 뒤에 체이닝하는 `select()`는 그 옵션을 받지 않는다. `select()`에 얹는 건 최초 조회(SELECT) 쿼리에서 count를 요청할 때 쓰는 패턴이라, mutation 뒤에 붙이면 형태가 다르다.

**해결**: `count`를 `update(updates, { count: 'exact' })`, `delete({ count: 'exact' })`처럼 mutation 호출 자체에 옮겼다. `select()` 체이닝 자체가 필요 없어져 코드도 한 줄 줄었다.

**검증**: 브라우저 콘솔에서 실제 로그인 세션으로 PATCH(선호도 수정 성공/404/이미 owned인 옷 재승격 차단)와 DELETE(성공/404)를 각각 호출해 응답 코드를 확인했다. 상세 화면에서는 별점·핏·착용빈도 클릭 → 즉시 저장 → 새로고침 유지, 삭제 확인 → `/wardrobe`로 리다이렉트 → 그리드에서 사라짐까지 실제로 눈으로 확인했다.

**결과**: Phase 3 완료. `npm test`(84개) 전부 통과.

### Phase 4 — 핏 판단 엔진 (2026-08-15)

`lib/fit/rules.ts`(허용편차·심각도·가중치 상수), `lib/fit/profile.ts`(선호 실측 범위 클러스터링), `lib/fit/engine.ts`(편차 채점), `lib/verdict.ts`(최종 판정)를 AI 없이 순수 함수로 만들고, `/api/analyze`·`/analyze`·`/cart` 화면까지 붙여 "AI 없이 이미 쓸 만한 제품"(스펙 §14)을 완성하는 게 목표였다.

**겪은 문제 — 직접 만든 테스트의 기대값이 스펙 공식을 잘못 계산함**

**문제**: `scoreDeviation`(편차 채점) 테스트 두 개가 실패했다. "범위 밖으로 2cm 초과했으니 경고 점수" 같은 케이스에서 기대한 점수가 실제 결과와 달랐다.

**원인**: 스펙의 편차 공식은 `[lo, hi]`(선호 범위) 자체가 아니라 `[lo - t, hi + t]`(허용 편차만큼 넓힌 구간) 밖으로 벗어난 만큼을 `excess`로 잡는다. 테스트를 짤 때 이 확장 구간을 빼먹고 원래 범위 `[lo, hi]` 기준으로 "2cm 초과"를 계산해 값을 골랐다 — 실제로는 허용 편차(예: 총장 t=3.0)만큼 이미 여유가 있어서, 그 값은 여전히 허용구간 안이라 0점이 나오는 게 정답이었다. 코드(`lib/fit/engine.ts`)가 틀린 게 아니라 테스트 예시 수치가 스펙 공식을 잘못 대입한 경우였다.

**해결**: 허용구간 `[lo-t, hi+t]`을 먼저 계산한 뒤 그 밖으로 벗어나는 값을 역산해서 테스트 수치를 다시 골랐다(경고: 허용구간 밖 2cm, 심각: 허용구간 밖 5cm). 계획 문서의 테스트 예시 코드도 같은 실수가 있어 함께 고쳤다.

**겪은 문제 — Supabase JS의 `.returns<T>()`가 deprecated**

**문제**: `lib/fit/profile.ts`의 DB 집계 쿼리에 `.returns<GarmentRow[]>()`를 썼더니 에디터에 deprecated 경고가 떴다(빌드는 통과하지만).

**해결**: 같은 라이브러리 소스에서 `@deprecated Use overrideTypes<yourType, { merge: false }>() method` 안내를 확인하고 `.overrideTypes<GarmentRow[], { merge: false }>()`로 교체했다. `/cart` 화면의 비슷한 캐스팅도 처음부터 이 방식으로 맞춰 작성했다.

**검증**: `lib/fit/rules.ts`·`profile.ts`(클러스터링+선호 프로필)·`engine.ts`(채점)·`verdict.ts`를 단위 테스트로 촘촘히 검증(스펙 §9의 크롭/오버핏 다중 범위 예시, 회피 신호, 치명 위반, 데이터 부족 분기 포함)한 뒤, `/api/garments`가 옷장/장바구니 등록 로직을 공유하도록 리팩터(`lib/garments/register.ts`)했다. 실제 무신사 링크로 `/analyze`에서 판단 → 배지·"데이터 부족" 안내 확인 → `/cart`에서 방금 분석한 옷 확인 → "샀어요" → `/wardrobe`로 이동까지 브라우저에서 전체 플로우를 검증했다.

**결과**: Phase 4 완료 기준(AI 없이 결정론적 리포트 표시) 충족. `npm test`(87개) 전부 통과.

### Phase 5 — Gemini 연동 (2026-08-15)

등록 시 이미지 1장으로 스타일 태깅(`lib/ai/tagger.ts`), 편차 리포트+태그를 Gemini에 보내 매칭 심각도·피드백 문장을 받는 것(`lib/ai/advisor.ts`)까지가 목표였다. **최종 판정은 항상 코드가 계산하고 Gemini는 서술만 한다**는 원칙(스펙 §9-10)을 그대로 지켰다.

**겪은 문제 — 스펙에 명시된 `gemini-2.5-flash`가 신규 발급 API 키에서 404**

**문제**: `GEMINI_API_KEY`를 새로 발급받아 태깅을 처음 실행하자 `ApiError: This model models/gemini-2.5-flash is no longer available to new users.`가 났다.

**원인**: 스펙 작성 시점(2026-08-13)에는 유효했던 모델이, 그 사이 Google이 신규 사용자 대상 접근을 막은 것으로 보인다. `client.models.list()`로 이 API 키가 실제로 쓸 수 있는 모델 목록을 직접 조회해보니 `gemini-2.5-flash`는 카탈로그에는 여전히 나열되지만(`generateContent` 호출 시점에만 별도로 막힘), `gemini-3.5-flash`·`gemini-3.7-flash`·`gemini-flash-latest` 등 더 최신 flash 계열은 정상 호출됐다.

**해결**: 사용자에게 상황을 알리고 대안(구체적 버전 고정 vs `gemini-flash-latest` 별칭)을 물어, `gemini-3.5-flash`로 교체하기로 했다. `CLAUDE.md`·설계 스펙(§4, §10)·계획 2 문서의 모델명을 전부 갱신해 실제 코드와 문서가 어긋나지 않게 했다. `/api/analyze`에서는 모델명을 문자열로 반복해서 하드코딩하지 않고 `GEMINI_MODEL` 상수를 참조하도록 해, 다음에 또 모델을 바꿔야 할 때 한 곳만 고치면 되게 했다.

**겪은 문제 2 — Gemini `responseSchema`는 표준 JSON Schema가 아니다**

**문제**: 구조화 출력 스키마의 `type` 필드에 JSON Schema 관례대로 `'object'`/`'string'`(소문자)을 썼는데, TypeScript는 통과했지만(`SchemaUnion = Schema | unknown`이라 타입 체크가 사실상 무력화됨) 실제로 스키마가 적용되는지 의심스러웠다.

**해결**: SDK 타입 정의(`node_modules/@google/genai/dist/genai.d.ts`)에서 `Type` enum을 확인했다 — Gemini의 스키마는 `Type.OBJECT`/`Type.STRING`처럼 대문자 상수를 쓴다. `lib/ai/tagger.ts`·`lib/ai/advisor.ts` 둘 다 `Type` enum으로 작성해 실제로 정상 동작하는 것까지 확인했다.

**겪은 문제 3 — Vitest mock에서 연속 실패(재시도) 테스트가 잡히는 예외를 unhandled rejection으로 오탐지**

**문제**: "한 번 실패하면 재시도하고, 재시도까지 실패하면 null" 테스트에서 `generateContentMock.mockRejectedValue(...)`(또는 `mockImplementation(() => Promise.reject(...))`)을 쓰면, 실제로는 `try/catch`로 잡히는 에러인데도 테스트가 `Error: timeout`으로 실패했다.

**원인**: 최소 재현으로 좁혀보니 `vi.mock()` 팩토리로 대체한 모듈을 통해 같은 mock 함수를 연속으로 두 번 호출·reject시키는 조합에서만 재현됐다 — `vi.fn()`을 직접 함수 인자로 넘기는 단순한 경우는 문제없었다. Vitest의 mock 계측(호출 결과 기록)과 이 조합이 상호작용해 실제로는 처리되는 rejection을 처리 안 된 것으로 오탐지하는 것으로 보인다.

**해결**: `mockRejectedValueOnce(...).mockRejectedValueOnce(...)`처럼 호출 횟수만큼 순서대로 등록하는 방식으로 바꾸니 정상 통과했다. `tests/ai/advisor.test.ts`와 계획 문서에 원인과 함께 남겨, 다음에 같은 패턴(vi.mock + 연속 reject)을 쓸 때 같은 삽질을 반복하지 않게 했다.

**검증**: 등록 시 실제 무신사 상품 이미지로 태깅을 실행해 `ai_tags`가 (카테고리·색상·톤·패턴·스타일 키워드·격식도·계절) 구조로 정확히 채워지는 것을 확인했다. `/api/analyze`에서는 정상 키로 호출해 4개 피드백 문장(요약·사이즈·매칭·가격)이 자연스러운 한국어로 나오고 `analyses.feedback`·`model`·`prompt_snapshot`이 채워지는 것을 확인한 뒤, `GEMINI_API_KEY`를 일부러 무효한 값으로 바꿔 같은 요청을 다시 보내 `feedback: null`·`fit_score`만으로 판정되는 폴백 경로(스펙 §12)까지 실제로 재현해 확인했다. 테스트로 생성한 옷·분석 결과는 검증 후 정리했다.

**결과**: 계획 2(선호도·핏 판단·Gemini·장바구니, 스펙 Phase 3~5) 완료. `npm test`(93개) 전부 통과, `npm run build` 타입 오류 없이 성공.

### Phase 6~8 — 공유 옷장 · 룩 · 마감 (2026-08-16)

옷장 공유 토글, 공개 열람(`/u/[share_slug]`), 로그인한 방문자의 추천 아이템 등록·룩 만들기, `/looks` 목록, 공유 링크 OG 이미지, 로딩 상태까지가 목표였다. 이걸로 스펙 §14의 Phase 0~8 전체가 끝난다.

**이번 Phase가 유난히 순조로웠던 이유**: 계획 1(Phase 1) 시점에 이미 `garments_insert` RLS 정책을 "본인 옷장에는 자유롭게, 남의 공개 옷장에는 `status='considering'`으로만" 넣도록 짜두었고, `garments` 테이블에도 `recommended_by`·`note` 컬럼을 처음부터 만들어뒀다. 그 덕분에 이번 계획에서 "친구 추천" 기능은 새 권한 로직을 거의 안 짜고, `lib/garments/register.ts`(계획 2)에 필드 두 개를 얹고 얇은 API 하나(`/api/recommend`)를 추가하는 것으로 끝났다 — 미리 해둔 설계 투자가 두 계획 뒤에 실제로 보상받은 사례였다.

**겪은 문제 — Satori(`next/og`)가 `{표현식}텍스트` 혼합 자식을 별도 노드로 갈라 500 에러를 냄**

**문제**: 공유 링크 OG 이미지(`app/u/[share_slug]/opengraph-image.tsx`)를 브라우저에서 직접 열어보니 500 에러였다. dev 서버 로그에는 `Expected <div> to have explicit "display: flex" ... if it has more than one child node`라는 원인이 찍혔는데, 정작 문제의 `<div>`에는 이미 `display: flex`를 명시해둔 상태였다.

**원인**: 에러가 가리킨 건 바깥쪽 컨테이너가 아니라 `<div>{nickname}님의 옷장</div>`처럼 JSX 표현식과 리터럴 텍스트가 섞인 안쪽 `<div>`였다. Satori(`next/og`의 렌더링 엔진)는 이 경우 `{nickname}`과 `"님의 옷장"`을 서로 다른 자식 노드 두 개로 쪼개서 받아들여, "자식이 2개 이상이면 명시적 `display`가 필요하다"는 검사에 걸린다 — 화면에는 이어 붙어 보이는 한 줄짜리 텍스트라도 Satori 입장에서는 복수 자식이었다.

**해결**: `{nickname}님의 옷장` → `{`${nickname}님의 옷장`}`처럼 템플릿 리터럴로 감싸 항상 텍스트 노드 하나만 전달되게 고쳤다. 표현식과 한글 텍스트를 같은 줄에 섞어 쓰는 흔한 패턴이 이 렌더링 엔진에서는 함정이라는 걸 실제로 500을 만나고서야 알았다.

**검증**: `outfits`/`outfit_items` RLS는 5개 시나리오(공개 옷장에 타인이 룩 생성, 그 옷장 소유가 아닌 옷은 룩에 못 넣음, 본인 옷장이어도 비공개면 룩을 못 만듦 — 스펙 §7 원문 그대로 "본인 예외 없음"까지 확인, 옷장 주인의 삭제 권한)를 실제 원격 DB에 두 사용자로 검증했다. Chrome 확장이 세션 중 반복적으로 끊겨서, UI로 못 본 구간(추천 등록·룩 생성)은 `registerGarment`/`/api/outfits`를 테스트 계정과 실제 로그인 세션으로 직접 호출해 DB 반영과 롤백(옷장 소유가 아닌 옷이 섞이면 방금 만든 `outfits` 행을 지우는 로직)까지 확인했다. 연결이 복구된 뒤에는 실제 브라우저로 공유 링크 공개/비공개 전환(200/404), 본인 옷장 방문 시 추천·룩 섹션이 정확히 숨겨지는 것, `/looks`의 제작자·썸네일 렌더링, OG 이미지·메타 태그까지 눈으로 확인했다. 테스트로 만든 룩·추천 아이템은 검증 후 모두 정리했다.

**결과**: 계획 3(공유 옷장·친구 추천·룩, 스펙 Phase 6~8) 완료. `npm test`(98개) 전부 통과, `npm run build` 타입 오류 없이 성공. 이걸로 `docs/superpowers/specs/2026-08-13-buy-or-not-design.md`에 정의된 전체 범위(Phase 0~8)가 구현됐다.

### 계획 4 — 네비게이션 & 디자인 시스템 (2026-08-17)

스펙 범위(Phase 0~8) 구현이 끝난 뒤 직접 써보니 화면 간 이동 수단이 전혀 없고(옷장 상세에서 뒤로 갈 방법도 없음), UI가 Tailwind 기본 회색·검정뿐이었다. `app/(app)/` 라우트 그룹으로 PC 헤더/모바일 하단 탭바를 공통 적용하고, `docs/superpowers/specs/2026-08-16-nav-and-design-system.md`에서 정한 웜톤 디자인 토큰(`--color-canvas` 등)과 공통 프리미티브(`Button`, `CARD_SURFACE`, `pillClass`)로 기존 화면 전체의 하드코딩 색을 걷어내는 게 목표였다.

**겪은 문제 — CSS 주석 안의 `*/`가 주석을 일찍 끊어버림**

**문제**: `app/globals.css`의 `@theme` 블록 위에 설명 주석을 달았는데, `npm run build`가 "Unexpected token Delim('*')"라는 CSS 파싱 경고를 냈다.

**원인**: 주석 문장 안에 "`--color-*` 를 `bg-*/text-*/border-*` 로"처럼 별표를 코드 표기용으로 섞어 썼는데, 그중 `*/` 시퀀스가 CSS 블록 주석의 닫는 토큰과 우연히 일치해 주석이 의도한 위치보다 훨씬 앞에서 끝나버렸다. 이후 실제 코드로 남아있던 주석 나머지 텍스트를 Lightning CSS가 CSS 문법으로 파싱하려다 걸린 경고였다.

**해결**: 주석 문장에서 `*/`가 만들어지는 조합(`-*` 뒤에 바로 `/`)을 피해 "`--color-x`를 `bg-x`, `text-x`, `border-x`로"처럼 풀어 썼다. CSS 파일에 주석을 달 때는 별표(`*`)와 슬래시(`/`)가 붙는 조합 자체를 조심해야 한다는 걸 실제 경고로 확인했다.

**겪은 문제 — Windows에서 `git mv`로 디렉터리 전체를 옮기지 못함**

**문제**: 인증 화면들을 `app/(app)/` 라우트 그룹으로 옮기려고 `git mv app/wardrobe "app/(app)/wardrobe"`(디렉터리 단위)를 실행했더니 "Permission denied"로 실패했다. `app/analyze`·`app/cart`·`app/looks`는 같은 명령으로 문제없이 옮겨졌는데 `app/wardrobe`만 실패했다.

**원인**: Windows에서는 파일시스템 핸들이 열려 있는 디렉터리(이 경우 `next dev`가 감시 중이던 디렉터리로 추정)를 통째로 rename하는 동작이 막힐 수 있다 — 유닉스 계열과 달리 디렉터리 이동이 원자적 rename 한 번으로 안전하게 처리되지 않는다.

**해결**: 디렉터리째 옮기는 대신 `git mv app/wardrobe/page.tsx "app/(app)/wardrobe/page.tsx"`처럼 파일 단위로 하나씩 옮기고, 빈 디렉터리만 `rmdir`로 정리했다. 파일 단위 이동은 Git 이력(rename으로) 그대로 보존됐다.

**겪은 문제 — 아이콘 라이브러리 export 이름을 Windows 파일시스템이 잘못 검증해줌**

**문제**: 계획 단계에서 `@phosphor-icons/react`가 실제로 `Coathanger`라는 이름을 export하는지 미리 확인했고(파일 존재 확인으로 "OK") 그 이름으로 코드를 작성했는데, 정작 `npm run build`에서 "Export Coathanger doesn't exist ... Did you mean to import CoatHanger?"로 실패했다.

**원인**: 실제 export 이름은 `CoatHanger`(H 대문자)였다. 사전 검증에 쓴 `ls node_modules/.../Coathanger.d.ts` 같은 파일 존재 확인이 Windows의 대소문자 구분 없는 파일시스템 때문에 실제로는 다른 대소문자의 `CoatHanger.d.ts`와 매치되어 "존재함"으로 잘못 통과됐다 — 파일 존재 여부만으로는 정확한 대소문자를 검증할 수 없었다.

**해결**: 빌드 에러가 정확한 이름을 알려줘서 `CoatHanger`로 고쳤다. 이후 나머지 아이콘 이름들은 `grep -x`(정확히 일치하는 줄만 매치)로 대소문자까지 정확히 비교해 재검증했다.

**검증**: 로그인한 브라우저로 PC 폭에서 헤더의 5개 메뉴(옷장·살까말까·장바구니·룩·마이페이지)를 모두 클릭해 실제 이동과 활성 탭 강조를 확인하고, 옷장 상세(`/wardrobe/[id]`)처럼 하위 경로에서도 "옷장" 탭이 계속 켜져 있는 것(Task 2에서 TDD로 만든 `isActiveNav`가 실제로 하는 일)을 확인했다. `/mypage`에서 구글 아바타·닉네임 표시, 공유 토글 이전, 로그아웃 후 `/`로 리다이렉트, 비로그인 상태로 `/wardrobe` 직접 접근 시 리다이렉트까지 실제 계정으로 로그아웃·재로그인해가며 확인했다. `/analyze`에서 실제 무신사 링크로 판정까지 끝까지 진행해 새 배지·편차 표 스타일을 확인한 뒤 테스트로 만든 분석 데이터는 정리했다. `/u/[share_slug]`는 로그인 상태(내 옷장으로 링크)와 `curl`로 뜬 비로그인 상태(로그인 링크) 양쪽을 확인했다. 모바일 하단 탭바는 이 세션의 브라우저 자동화 도구가 뷰포트 리사이즈를 반영하지 못해 픽셀 단위로는 확인하지 못했다 — 대신 `md:hidden`/`hidden md:block`이라는 표준 Tailwind 브레이크포인트 클래스가 정확히 적용됐음을 코드로 확인했다.

**결과**: 계획 4(네비게이션 & 디자인 시스템, `docs/superpowers/plans/2026-08-16-plan4-nav-and-design-system.md`) 1단계 완료. `npm test`(103개) 전부 통과, `npm run build` 타입 오류 없이 성공. 핏 판단 설정(2단계)은 마이페이지에 진입점만 만들어두고 별도 스펙·계획으로 이후 진행한다.

### 부록 — 카테고리 오분류 버그 수정 (2026-08-17)

계획 4를 쓰던 중 실제로 옷장을 써보다가 발견한 문제: 팔찌를 등록했더니 "상의"로 저장됐고, 신발·액세서리를 등록할 때도 총장·가슴단면 같은 상의용 실측 입력칸이 그대로 떴다.

**원인**: `lib/musinsa/parser.ts`의 `MUSINSA_CATEGORY_MAP`이 무신사 대분류명 중 일부(주얼리 등 액세서리 세부 분류로 추정)를 몰라 파싱이 실패했고, `components/GarmentForm.tsx`가 파싱 실패 시 기본값을 `'top'`으로 채워 넣어서 사용자가 놓치면 그대로 저장됐다. 실측 입력 폼도 `FIT_RULES`에 `shoes`/`acc`가 원래 없다는 걸 폼이 반영하지 않고 모든 카테고리에 무조건 그렸다.

**해결**: (1) 실측 "Field"를 `category in FIT_RULES`일 때만 렌더링해 신발·액세서리에는 아예 안 뜨게 했다. (2) 카테고리 파싱 실패 시 기본값을 `'top'`에서 `'acc'`로 바꿨다 — 잘못 등록돼도 핏 판단(FIT_RULES에 없는 카테고리는 채점을 건너뜀)을 오염시키지 않는 안전한 카테고리로 떨어지게 한 것이다. 팔찌의 실제 무신사 대분류명을 확인 못 해 `MUSINSA_CATEGORY_MAP` 자체는 넓히지 않았다 — 이 프로젝트가 Phase 0부터 지켜온 "실제 페이지로 검증 후 반영" 원칙상 근거 없이 카테고리명을 추측해 넣지 않았다.

**검증**: 브라우저에서 카테고리 드롭다운을 "액세서리"로 바꾸면 실측 섹션이 즉시 사라지고, "상의"로 되돌리면 즉시 다시 나타나는 것을 확인했다.

**결과**: `npm test`(103개) 전부 통과. `MUSINSA_CATEGORY_MAP` 확장은 실제 액세서리 상품 링크를 확보하면 이어서 진행하기로 계획 5 문서에 남겨뒀다.

### 계획 5 — 핏 판단 강도 설정 (2026-08-17)

`lib/fit/rules.ts`의 `FIT_RULES`는 카테고리별 14개 항목 × (허용편차·심각도·가중치) 총 45개 숫자로 이뤄져 있어 전부를 설정 화면에 노출하기엔 과했다. 그래서 허용편차에만 곱해지는 배율 하나(0.5배~2.0배 슬라이더)로 범위를 좁혔다. `docs/superpowers/specs/2026-08-17-fit-strictness-design.md`가 설계 근거다.

이번 계획은 겪은 문제보다 미리 잡아둔 설계 제약이 실제로 효과가 있었던 사례에 가깝다.

**설계 판단 1 — `buildPreferenceProfile`과 `scoreDeviation`에 반드시 같은 배율을 넘겨야 한다는 제약**

핏 판단은 "선호 실측값들을 허용편차 이내로 묶어 구간을 만드는 단계"(`buildPreferenceProfile`)와 "후보 옷이 그 구간 밖으로 얼마나 벗어났는지 재는 단계"(`scoreDeviation`)로 나뉘는데, 둘 다 같은 허용편차를 `[lo-t, hi+t]` 확장구간 계산에 쓴다. 배율을 두 곳에 각자 다르게 넘기면 이 전제가 깨진다는 걸 스펙 단계에서 미리 인지해, `/api/analyze`가 `profiles`에서 배율을 딱 한 번만 읽어 양쪽에 같은 값을 넘기도록 계획을 짰다. 실제 구현·종단 검증까지 이 부분에서 별도로 발견된 버그는 없었다 — 처음부터 제약으로 못박아 둔 게 그대로 맞아떨어진 경우다.

**설계 판단 2 — 슬라이더 저장을 `onChange`가 아니라 `onPointerUp`/`onKeyUp`에서 하기**

`<input type="range">`의 `onChange`는 드래그하는 동안 값이 바뀔 때마다 발생한다. 화면 표시는 `onChange`로 즉시 갱신하되 저장(`PATCH /api/profile`)은 손을 뗄 때만 하도록 나눴다. 브라우저 네트워크 탭으로 직접 확인한 결과, 드래그 한 번(수십 번의 값 변화)에 PATCH가 정확히 1번만 나갔다.

**검증**: 상의 3벌(총장 60·62·72.5cm, 별점 5점)을 등록해 선호 구간이 `[60,62]`와 `[72.5,72.5]` 두 클러스터로 나뉘게 만든 뒤, 총장 65cm인 후보 옷을 강도 0.5배와 2.0배로 각각 판단했다. 0.5배(허용편차 1.5cm)에서는 "1.5cm 초과"로 주의 판정이, 2.0배(허용편차 6.0cm)에서는 "적합"으로 살만함 판정이 나왔다 — 계획 문서에 미리 손으로 계산해 둔 값과 정확히 일치했다. 검증용으로 만든 옷·분석 데이터는 확인 후 정리했고, 슬라이더는 기본값(1.0배)으로 되돌려 뒀다.

**결과**: 계획 5(핏 판단 강도 설정, `docs/superpowers/plans/2026-08-17-plan5-fit-strictness.md`) 완료. `npm test`(107개) 전부 통과, `npm run build` 타입 오류 없이 성공.
