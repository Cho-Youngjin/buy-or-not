# 장바구니 가격 인하 표시 설계 문서

작성일: 2026-08-17

## 1. 배경

합의한 A~F의 마지막, **F: 가격 인하 표시**. 장바구니(살까 말까 고민 중, `status='considering'`)에 담아둔 무신사 상품의 가격이 떨어지면 "원래 얼마 → 지금 얼마"를 보여준다. 사용자가 처음 제안한 이메일 알림·마이페이지 알림 토글은 뺐고(원래 설계 스펙 §3이 애초에 "알림, 가격 인하 추적"을 제외 항목에 넣어뒀던 결정을 되살리는 셈이다), 일정 주기(원안 "일주일")마다만 재확인해 무신사에 너무 자주 요청을 보내지 않게 한다.

## 2. 재확인 트리거 — Vercel Cron 대신 방문 시 지연 확인

**사용자 확인**: 진짜 백그라운드 자동 실행(Vercel Cron)이 아니라, **`/cart` 방문 시 지연 확인**으로 간다. 이 프로젝트는 아직 실제 Vercel에 배포된 흔적이 없어(`vercel.json` 없음), Cron은 배포 후에만 동작하고 로컬에서는 테스트할 방법이 없다. 방문 시 지연 확인은 배포 여부와 무관하게 지금 바로 만들고 테스트할 수 있다.

## 3. 데이터 모델

`garments`에 컬럼 두 개를 추가한다(새 테이블은 만들지 않는다 — 필요한 건 "원래→지금" 한 쌍이지 가격 이력 전체가 아니다):

```sql
alter table garments
  add column last_known_price integer check (last_known_price is null or last_known_price >= 0),
  add column price_checked_at timestamptz;
```

기존 `garments_update` RLS 정책(`owner_id = auth.uid()`, `supabase/migrations/0002_rls.sql`)이 이미 이 두 컬럼도 커버한다 — 새 정책이 필요 없다.

## 4. 재확인 대상과 절차

**대상**: 로그인 사용자 소유 + `status='considering'`(장바구니) + `source_url is not null`(무신사 링크로 등록된 것만 — 계획 8의 수동 등록 아이템은 `source_url`이 없어 자연히 제외된다) + `price_checked_at`이 `null`이거나 **7일** 이상 지난 것.

**절차**(`POST /api/cart/refresh-prices`):
1. 위 조건으로 대상을 조회한다. `price_checked_at`이 오래된(또는 아예 없는) 순으로 정렬해 **최대 5개**만 가져온다 — 오랜만에 방문해 장바구니가 많이 쌓여 있어도 한 번에 몰아서 긁지 않는다(나머지는 다음 방문에 처리된다).
2. 각 아이템의 `source_url`을 기존 파싱 파이프라인(`fetchProductHtml` → `parseProductHtml`)에 그대로 넣어 **가격 필드만** 다시 읽는다. 새 파싱 로직을 만들지 않는다.
3. 가격을 성공적으로 읽었으면 `last_known_price`를 갱신한다. 실패해도(네트워크 오류, 가격 필드 파싱 실패 등) **`price_checked_at`은 갱신한다** — 상품이 삭제됐거나 페이지 구조가 바뀌어 계속 실패하는 링크를 방문할 때마다 재시도하지 않기 위해서다.
4. 몇 개를 갱신했는지 응답으로 돌려준다.

## 5. UI

`/cart`에 눈에 보이지 않는 클라이언트 컴포넌트(`CartPriceRefresher`)를 하나 두고, 마운트되자마자 위 API를 백그라운드로 부른다 — 페이지 첫 로딩은 막지 않는다. 응답에 갱신된 항목이 있으면 `router.refresh()`로 화면을 다시 그린다.

`CartItemCard`에 가격을 추가한다(지금은 가격이 아예 표시되지 않고 있다):

- `last_known_price`가 `price`보다 **낮을 때만**: `19,900원` 취소선 + `→` + `15,900원`(강조) + "인하" 배지(`pillClass('buy')` 재사용 — 톤이 긍정적 신호와 맞는다).
- 그 외(안 내렸거나 아직 확인 전): 알고 있는 가장 최근 가격(`last_known_price ?? price`)만 평범하게 표시한다.

## 6. 에러 처리

- 무신사 요청이 실패해도(타임아웃·구조 변경 등) 장바구니 화면 자체는 항상 정상 렌더링된다 — 가격 갱신은 부가 기능이라 실패해도 사용자를 막지 않는다(§4-3의 "실패해도 `price_checked_at` 갱신" 원칙과 같은 방향).
- `/api/cart/refresh-prices`는 로그인하지 않은 요청을 401로 거부한다. 그 외에는 항상 200을 돌려준다(개별 아이템 실패는 응답 안에서 조용히 처리되고, 클라이언트는 성공/실패를 구분해 보여줄 필요가 없다 — 사용자가 신경 쓸 일이 아니다).

## 7. 테스트

- **파싱 로직 자체는 새로 만들지 않으므로**(기존 `parseProductHtml`을 그대로 재사용) 새 단위 테스트가 크게 필요하지 않다. "7일 지남" 판정처럼 순수하게 계산 가능한 부분(예: 대상 필터링 조건)이 있다면 그 부분만 짧게 테스트한다.
- 브라우저 수동 검증: DB에서 특정 장바구니 아이템의 `price_checked_at`을 8일 전으로 되돌려 놓고 `/cart`를 방문 → `last_known_price`가 갱신되는지, 가격이 실제로 내려간 상품이면(또는 테스트로 DB에서 `price`를 인위적으로 높여) "원래→지금" 표시가 뜨는지 확인한다.

## 8. 범위 밖

- **이메일·마이페이지 알림 토글** — 사용자가 이미 명시적으로 뺀 범위(계획 6 문서).
- **가격 이력 전체 저장·그래프** — "원래→지금" 한 쌍이면 충분하다고 판단했다(§3).
- **Vercel Cron 기반 완전 자동 갱신** — 이번엔 방문 시 지연 확인으로 간다(§2). 나중에 실제 배포 후 필요해지면 이 방문-트리거 로직(`/api/cart/refresh-prices`)을 그대로 Cron에서도 호출할 수 있다 — 지금 설계를 버리지 않아도 된다.
- **`considering` 이외 상태(예: `owned`)의 가격 추적** — 요청 범위가 "장바구니 상품"으로 명확히 한정돼 있다.
